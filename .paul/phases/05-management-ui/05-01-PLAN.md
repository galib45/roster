<objective>
## Goal

Build the management UI layer so administrators can create and edit organizations, rosters, employees, and shift templates — all persisted to the project file with proper validation and unsaved-change awareness.

## Purpose

The solver (Phase 4) produces optimal rosters, but admins need to configure the input data: who works where, what shifts exist, and what the rules are. This phase builds the forms, lists, and dialogs for that configuration, using the GPUI Kit's sidebar navigation and component library.

## Output

- `src/ui/organizations.rs` — Organization list page, add/edit dialog
- `src/ui/rosters.rs` — Roster list per organization, add/edit dialog with staff isolation
- `src/ui/employees.rs` — Employee CRUD: name, position, skills, roster assignment
- `src/ui/shifts.rs` — Shift template CRUD: name, start/end, required positions with headcounts
- Sidebar integration: Organizations page as root, Rosters/Employees/Shifts as child pages
- Validation: real-time field validation, unsaved-change warnings before navigation
- All mutations go through `Organization` methods (reuse Phase 2 domain logic)
</objective>

<design>
## Architecture

### Page Structure (extends Phase 1 `App::Page`)

```rust
enum Page {
    Organizations,
    OrganizationDetail { org_id: String },
    Rosters { org_id: String },
    RosterDetail { org_id: String, roster_id: String },
    Employees { org_id: String },
    EmployeeDetail { org_id: String, employee_id: Option<String> }, // None = new
    Shifts { org_id: String },
    ShiftDetail { org_id: String, shift_id: Option<String> },      // None = new
}
```

Sidebar shows:
- Organizations (top-level)
- When an org is selected: Rosters, Employees, Shifts as child items

### State Management

Each detail page holds a `Draft` struct mirroring the entity:
- `DraftEmployee { name, position_id, skills, roster_id }`
- `DraftShift { name, start, end, weekdays, requirements: Vec<DraftRequirement> }`
- `DraftRequirement { position_id, headcount }`

On "Save": validate → call domain method → on success, replace draft with saved entity, clear dirty flag.

On "Cancel" or navigation away with dirty flag: show confirmation dialog.

### Validation Strategy

- **Field-level**: empty name → inline error; invalid time → inline error
- **Cross-field**: employee position must exist in org; shift requirement position must exist
- **Business rules**: `Organization` methods return `DomainError`; surface as toast + inline

### GPUI Kit Components Used

| Need | Component |
|------|-----------|
| Sidebar | `gpui_kit::component::sidebar::Sidebar` |
| Form fields | `gpui_kit::component::form::*` (TextInput, Select, TimePicker) |
| Dialogs | `gpui_kit::component::dialog::Dialog` |
| Tables | `gpui_kit::component::table::Table` |
| Toasts | `gpui_kit::component::toast::Toast` |
| Buttons | `gpui_kit::component::button::Button` |

### Persistence

- Every successful save calls `save_project(&project)` (Phase 1 store)
- Project loads on startup; `App` holds `Arc<Mutex<Project>>` or similar
- No auto-save: explicit Save button per form

## UI Flows

### Organizations Page
- List all orgs (name, roster count, employee count)
- "Add Organization" → dialog with name field → `Organization::new`
- Click org → navigate to OrganizationDetail (or Rosters for that org)

### Rosters Page (per org)
- List rosters (name, shift count, sharing group count)
- "Add Roster" → dialog with name → `org.add_roster`
- Click roster → RosterDetail (shows shifts, sharing groups, plans)

### Employees Page (per org)
- List employees (name, position, roster, skills)
- "Add Employee" → dialog: name, position (select), roster (select), skills (comma-separated)
- `org.add_employee` validates roster membership + position match
- Edit: pre-fill draft, same dialog

### Shifts Page (per org)
- List shift templates (name, time, weekdays, requirements)
- "Add Shift" → dialog: name, start/end time, weekdays (checkboxes), requirements table
- Requirements: add rows with position (select) + headcount (number)
- `org.add_shift` + `org.require_position` for each requirement

## Error Handling

- Domain errors (`DomainError`) → toast with user-friendly message
- Validation errors → inline field errors + disabled Save button
- Network/storage errors (save_project) → toast, keep draft intact
</design>

When I create shift "OPD" 08:00–14:00, weekdays Mon–Fri, requirements: Doctor×2, Nurse×1
