# Phase 5 Plan 04: Template/Roster Domain Re-baseline

<objective>

## Goal

Replace the staff-group roster model with reusable **roster templates** and standalone **dated rosters**: employees belong to the organization and hold one position, a template auto-includes all employees holding its selected positions (minus explicit exclusions), and a dated roster is created from a template with a start/end range, snapshots its members and shift occurrences, and moves through Draft → Generated → Finalized.

## Purpose

The approved workflow cannot be expressed by `Employee.roster_id` plus a `Roster` that embeds every plan:

- Staff must be gathered by position, not assigned manually to a roster.
- A template must be reusable across periods, with per-template exclusions.
- A dated roster must be a first-class object the admin creates before generation, then edits and finalizes.
- Removing `roster_id` and moving plans out of templates requires a schema change, so persistence must move to v3 with explicit migration.

This plan changes the domain, store, evaluation, and solver so the UI can be rebuilt on the new model in 05-05. Modal dialogs may remain temporarily; they are removed in 05-05.

## Output

- `RosterTemplate` (positions, exclusions, shifts, rest rules, sharing groups, dated rosters) and `Roster` (dated instance with snapshot members, dated shifts, context, status).
- `Employee` without `roster_id`.
- Organization methods for template membership, inclusion/exclusion, template CRUD, and dated roster creation.
- Schema v3 with v1 → v2 → v3 migration and round-trip tests.
- Evaluation and solver queries updated to use dated-roster members and position eligibility.
- A compiling, tested workspace; management UI adapted only enough to compile against the new names.

<design>

## Target domain shape

```rust
pub struct Organization {
    pub id: String,
    pub name: String,
    pub positions: Vec<Position>,
    pub employees: Vec<Employee>,
    pub roster_templates: Vec<RosterTemplate>,
}

pub struct Employee {
    pub id: String,
    pub name: String,
    pub position_id: String,              // exactly one position
    pub skills: Vec<String>,
    pub unavailability: Vec<Unavailability>,
    pub recurring_assignments: Vec<RecurringAssignment>,
}

pub struct RosterTemplate {
    pub id: String,
    pub name: String,
    pub position_ids: Vec<String>,        // positions this template covers
    pub excluded_employee_ids: Vec<String>,
    pub shifts: Vec<ShiftTemplate>,
    pub rest_rules: Vec<RestRule>,
    pub sharing_groups: Vec<SharingGroup>,
    pub rosters: Vec<Roster>,             // dated instances
}

pub struct RosterMember {
    pub employee_id: String,
    pub position_id: String,              // snapshot of the employee's position
}

pub struct Roster {
    pub id: String,
    pub template_id: String,
    pub name: String,                     // e.g. "Doctors — 2026-11-16 to 2026-11-30"
    pub start: NaiveDate,
    pub end: NaiveDate,
    pub status: PlanStatus,               // Draft, Generated, Finalized
    pub members: Vec<RosterMember>,       // snapshot at creation
    pub context: Vec<ContextAssignment>,
    pub shifts: Vec<DatedShift>,
}
```

- `ShiftTemplate` and `StaffingRequirement` keep their current fields. A requirement's position must be one of the template's `position_ids`; validation rejects otherwise.
- `DatedShift`/`ShiftSlot`/`ContextAssignment`/`PlanStatus` keep their current shape; `RosterPlan` is renamed to `Roster` and gains `template_id`, `name`, `start`, `end`, `members`, and `context`.
- Dated rosters snapshot `members` and expanded shifts at creation, so later template or staffing edits never rewrite an existing roster.
- `RosterTemplate.sharing_groups` and `rest_rules` remain live template metadata used by evaluation (matching current behavior).
- Membership: `Organization::template_members(template_id) -> Vec<&Employee>` selects employees whose `position_id` is in `position_ids` and whose id is not in `excluded_employee_ids`.

## Lifecycle

- `create_roster(template_id, start, end, context)`: validate template and dates, snapshot members, expand weekday-recurring shifts into dated shifts with one slot per required seat, status `Draft`.
- Generation (Phase 6) solves a `Draft` roster; `apply` sets `Generated`.
- Finalize (Phase 7) sets `Finalized`; assignment mutation on a finalized roster is rejected (existing rule).
- Creating a roster with start > end is rejected; context dates must be strictly before `start` (existing rule).

## Validation and errors

- Rename `EmployeeOutsideRoster` → `EmployeeNotInRoster`, `ShiftOutsideRoster` → `ShiftOutsideTemplate`, and update display messages. Add `PositionNotInTemplate { position_id, template_id }`.
- Adding an employee validates only `position_id`.
- Adding a shift/requirement validates that the roster is a template and the position is included.
- Assigning a slot validates: employee exists, the employee id appears in the dated roster's `members`, and the member's snapshot position matches the slot position.
- Shift-scoped unavailability and recurring assignments validate that the shift id exists in **some** template of the employee's organization (ids are globally unique), not only in the old employee roster.
- `Organization::validate()` checks: unique template names; unique position names; all template `position_ids` resolve; all exclusions resolve and hold an included position; every shift requirement position is included; every dated roster's `template_id` resolves; every `members` entry resolves and its snapshot `position_id` is included by the template; every assignment resolves to a member with the matching position.

## Store / migration

- `SCHEMA_VERSION = 3`; save writes v3.
- v2 fixture shape: organization has `rosters: Vec<RosterV2>`; each `RosterV2` has `shifts`, `rest_rules`, `sharing_groups`, `plans: Vec<RosterPlanV2>`; employees have `roster_id`.
- v2 → v3:
  - Each v2 roster becomes a `RosterTemplate` with the same id/name/shifts/rest_rules/sharing_groups.
  - `position_ids` = distinct positions of employees with that `roster_id` ∪ positions referenced by shift requirements.
  - `excluded_employee_ids` = empty.
  - Each v2 plan becomes a dated `Roster` with `template_id` = the template id, `members` = `RosterMember` entries for employees with that `roster_id` whose position is in `position_ids`, and the plan's dates/status/context/shifts.
  - Employees keep their position and drop `roster_id`.
- v1 → v2 migration stays intact and feeds v3.
- v3 serialization uses `roster_templates` and `rosters` on templates; `#[serde(default)]` on new collections.
- Store dispatch chooses the migration by `schema_version`; reject versions above 3 with the existing clear error.

## Compatibility for this plan

- Update eval/solver signatures to `(organization, template_id, roster_id, ...)`: the template supplies rest rules/sharing groups; the dated roster supplies members, shifts, and context.
- Keep the public solver entry points recognizable (`solve`, `apply`, `precheck`) but keyed by template + dated roster.
- UI code may keep dialogs for this plan; replace names and adapt employee (no roster select) and shift (template list) just enough to compile. 05-05 replaces the dialogs and page structure.
