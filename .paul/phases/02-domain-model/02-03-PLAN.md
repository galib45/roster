<objective>
## Goal

Turn shift templates into a concrete schedule: a `RosterPlan` for a date range containing dated shift instances, one slot per required seat, optional employee assignments, and the previous-day context — with per-template weekday occurrence, snapshot semantics, validation, and persistence. A roster keeps multiple plans (for example November and December).

## Purpose

Templates alone cannot produce a roster. The solver (Phase 4) needs one decision variable per seat; the constraint model (Phase 3) needs dated shifts and assignments to evaluate; the generate UI (Phase 6) and live editor (Phase 7) need the same structure and stable IDs. Modeling this now — still without any solver or UI — completes the Phase 2 domain and prevents a second schema rewrite.

## Output

- `ShiftTemplate.weekdays` (empty = every day) and an `occurs_on` helper
- `src/domain/plan.rs`: `RosterPlan`, `DatedShift`, `ShiftSlot`, `ContextAssignment`, `PlanStatus`
- `Roster.plans: Vec<RosterPlan>` (multiple saved periods)
- `Organization::generate_plan`, `assign_slot`, `unassign_slot`, and extended validation
- Store coverage for plan persistence and older v2 files without plans
- `tests/plan_generation.rs` with the 16–30 November 2026 example
</objective>

## Model

```text
Organization
├── positions, employees
└── rosters
    ├── shifts: Vec<ShiftTemplate>          // definitions (recurring by weekday)
    └── plans:  Vec<RosterPlan>             // generated periods
        ├── context: Vec<ContextAssignment> // day before start (read-only input)
        └── shifts:  Vec<DatedShift>        // one per template per active date
            └── slots: Vec<ShiftSlot>       // one per required seat
                └── employee_id: Option<String>
```

- A `ShiftTemplate` with headcount 2 produces **two** `ShiftSlot`s, not one slot with a count.
- `DatedShift` snapshots `name`, `start`, and `end` at generation time. `template_id` is provenance; editing a template later must not rewrite an existing plan.
- `employee_id: None` means unfilled; slots are never removed.
- Assignments must satisfy structural rules only: employee in the plan's roster and holding the slot's position. Overlap/leave/rest evaluation is Phase 3.

## November example
Roster "Doctors", 2026-11-16 → 2026-11-30 (15 days):
- OPD 08:00–14:00, 2 Medical Officer seats, every day **except Friday** → 13 dated shifts / 26 slots
- Emergency Morning 08:00–15:00, 1 seat, daily → 15 / 15
- Emergency Night 15:00–08:00, 1 seat, daily → 15 / 15
- Totals: **43 dated shifts, 56 slots**; Fridays are 2026-11-20 and 2026-11-27.

## AC-1: Templates instantiate into dated shifts with per-seat slots
```gherkin
Given roster "Doctors" with OPD (2 Medical Officer seats, every day except Friday), Emergency Morning (1 seat, daily), and Emergency Night (1 seat, daily)
When a plan is generated for 2026-11-16 through 2026-11-30 with no context
Then the plan has 43 dated shifts and 56 slots
And OPD exists on every date except 2026-11-20 and 2026-11-27
And each OPD dated shift has exactly 2 unfilled Medical Officer slots and each emergency shift has 1
And the Emergency Night dated shifts report a 1020-minute duration
And the plan status is Draft and its start/end dates match the request
And generating with an end date before the start date or an unknown roster is rejected
```

## AC-2: Employees are assigned to individual seats with structural validation
```gherkin
Given a generated Doctors plan and two Medical Officer employees in the Doctors roster
When one employee is assigned to the first OPD seat
Then that slot holds the employee id, the second OPD seat remains unfilled, and the other employee stays unassigned
And unassigning the slot clears it
And assigning an employee from another roster, an employee with a different position, an unknown employee, or an unknown slot is rejected
And assigning the same employee to a second seat of the same dated shift is rejected
And assigning to a finalized plan is rejected
```

## AC-3: Multiple plans, context, and persistence
```gherkin
Given a Doctors roster with a November plan and a December plan, each with context assignments for the day before their start
When the project is saved and loaded
Then both plans exist on the roster with their own ids, date ranges, statuses, dated shifts, slots, assignments, and context
And the loaded project equals the saved project exactly
And a v2 file written before this plan (no "plans" or "weekdays" fields) still loads with empty plans and daily shift templates
And the saved JSON contains roster-level "plans", dated "shifts", "slots", and an assignment "employee_id" (null when unfilled)
```

## AC-4: Generated plans are snapshots
```gherkin
Given a generated plan containing an "OPD" dated shift from 08:00 to 14:00
When the source template's name, times, or weekdays are edited afterwards
Then the existing dated shift keeps its original name, times, and slots
And a newly generated plan reflects the edited template
```

## AC-5: Validation catches corrupt plan data
```gherkin
Given a valid organization with plans
When it is mutated in memory so a plan's start is after its end, a slot points at a missing position, an assignment points at a missing employee, an assignment uses an employee from another roster or the wrong position, a context assignment uses an out-of-roster employee or a date on/after the plan start, or two dated shifts/slots share an id
Then `Organization::validate()` returns the corresponding DomainError naming the offending id
And a valid organization with context, slots, and assignments validates successfully
```
