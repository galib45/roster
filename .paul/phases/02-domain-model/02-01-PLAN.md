<objective>
## Goal

Model the definition side of the app with the corrected hierarchy — `Organization` owns positions and employees; `Organization` owns rosters; `Roster` owns shift templates — with validated constructors, stable IDs, strict staff isolation via `Employee.roster_id`, lossless serialization, and a tested migration from the Phase 1 `schema_version: 1` file.

## Purpose

Every later phase builds on these types: Phase 3 evaluates constraints over them, Phase 4 encodes them for Pumpkin, Phase 5 edits them in the UI, and Phase 6/7 produce and edit schedules against them. Getting the ownership boundaries and validation right now avoids a schema rewrite later. Bumping to schema 2 with an explicit migration keeps the promise that a Phase 1 project still opens.

## Output

- New domain modules: `organization`, `error`, `position`, `roster`, `employee`, `shift`, `migration`
- `ProjectFile` → `Organization` → (`positions`, `employees`, `rosters`)
- `Roster` → `shifts` only
- `Employee` references one `roster_id` and one organization-level `position_id`
- `ShiftTemplate` supports arbitrary start/end times, overnight durations, and required organization-level positions with headcounts
- `SCHEMA_VERSION = 2`; the store migrates v1 files and writes v2
- Unit tests plus an end-to-end `tests/phase2_domain.rs` fixture
</objective>

## Ownership Model (corrected)

```text
ProjectFile
└── Organization
    ├── positions:   Vec<Position>       // organization-level catalog
    ├── employees:   Vec<Employee>       // each has roster_id + position_id
    └── rosters:     Vec<Roster>
        └── shifts:  Vec<ShiftTemplate>  // rosters own shifts, nothing else
```

- `Employee.roster_id` is the isolation boundary: a Doctors-roster employee is never returned for the Nurses roster and may not own a Nurses shift.
- Positions are shared across the organization, so "Medical Officer" is defined once and referenced by both employees and shift staffing requirements.
- Cross-entity validation (employee → roster/position, shift requirement → position) lives on `Organization`, because `Roster` cannot see positions or employees.

## Reference Notes
- Follow the existing ID convention: `Uuid::new_v4().to_string()`.
- The project file derives `Serialize, Deserialize, Clone, Debug, PartialEq, Eq`; keep that for new types where possible (`NaiveTime` is `Eq`; do not add floats).
- `chrono` already has `serde` enabled; `NaiveDate`, `NaiveTime`, and `Weekday` serialize natively.
- The legacy prototype uses integer duty hours (OPD 6, Emergency Morning 7, Emergency Night 17). The generalized model derives duration from start/end instead; the legacy VALUES are reused as a parity fixture, not as enum variants.
- Do NOT edit `src/app.rs`: `ProjectFile::add_organization` keeps its current `Option<&Organization>` signature so the Phase 1 UI continues to compile unchanged.
- Keep `Organization` re-exported from both `domain::organization` and `domain` (and, if useful, `domain::project` for path compatibility). `src/app.rs` and `src/store/mod.rs` import through `crate::domain`, so they must keep compiling untouched.

## AC-1: Organizations own isolated rosters
```gherkin
Given a project with organization "City Hospital"
When the admin adds rosters "Doctors" and "Nurses"
Then each roster has a distinct generated id and exactly one owning organization
And the roster names are trimmed, blank names are rejected, and duplicate names in the same organization are rejected
And adding "Doctors" a second time returns an error and leaves the roster list unchanged
And a roster stores no employees or positions of its own
```

## AC-2: Employees and positions are organization-owned and roster-isolated
```gherkin
Given organization "City Hospital" with rosters "Doctors" and "Nurses" and position "Medical Officer"
When employees "Dr. Amit" and "Nurse Rina" are added
Then "Dr. Amit" can reference the Doctors roster and the Medical Officer position
And an employee whose roster_id or position_id does not exist is rejected
And listing employees for the Doctors roster returns only employees whose roster_id is Doctors
And the Nurses roster view cannot see "Dr. Amit"
And an employee or skill with a blank name is rejected
And employee and position ids survive a save/load round trip
```

## AC-3: Shifts live under rosters and require organization positions
```gherkin
Given organization "City Hospital" with positions "Medical Officer" and "Senior Staff Nurse" and roster "Doctors" with shift "Emergency Night" from 15:00 to 08:00
When the admin requires 2 Medical Officers and 1 Senior Staff Nurse, then raises Medical Officer to 3
Then the shift is found by id inside the Doctors roster and reports a 1020-minute duration with crosses_midnight() == true
And the shift has exactly two requirements with headcounts 3 and 1 (the duplicate position is updated, not duplicated)
And a shift added to an unknown roster is rejected
And a requirement for an unknown position, an unknown shift, or headcount 0 is rejected
And a normal 09:00–17:00 shift reports 480 minutes and a shift with equal start/end times is rejected
```

## AC-4: A full schema v2 project round-trips losslessly
```gherkin
Given a project with one organization, two rosters, organization positions, roster-assigned employees with skills, shifts, and staffing requirements
When the project is saved and loaded again
Then the loaded project equals the saved project exactly
And the saved JSON contains "schema_version": 2, top-level "positions"/"employees"/"rosters" under the organization, and shifts nested only inside rosters
```

## AC-5: Phase 1 files migrate; unknown schemas still fail safely
```gherkin
Given a schema_version 1 file containing organizations only
When it is loaded
Then every organization is preserved with its original id, name, and saved_at
And each organization has empty position, employee, and roster lists and the in-memory schema_version is 2
And saving that project writes schema_version 2
Given a schema_version 3 file
When it is loaded
Then the store returns UnsupportedSchema(3) and no partial project is produced
```

  <files>src/domain/mod.rs, src/domain/error.rs, src/domain/position.rs, src/domain/employee.rs, src/domain/shift.rs, src/domain/roster.rs, src/domain/organization.rs, src/domain/project.rs</files>
  <action>
    Create the definition-side domain with the corrected ownership. Keep one concern per module and avoid circular imports: `position`, `employee`, `shift`, and `roster` must not import `organization`; only `Organization` sees the whole graph.

    1. `src/domain/error.rs` — `DomainError` with `Display` + `std::error::Error` (no new dependency):
       `BlankName`, `DuplicateRoster { name }`, `DuplicatePosition { name }`, `DuplicateShift { name }`,
       `UnknownRoster { id }`, `UnknownPosition { id }`, `UnknownShift { id }`, `UnknownEmployee { id }`,
       `InvalidShiftTimes { start: NaiveTime, end: NaiveTime }`, `EmptyHeadcount { shift_id, position_id }`.
       Messages should name the offending value so the Phase 5 UI can surface them verbatim.

    2. `src/domain/position.rs`:
       `Position { id: String, name: String }` deriving `Serialize, Deserialize, Clone, Debug, PartialEq, Eq`.
       `Position::new(name) -> Result<Self, DomainError>` trims and rejects a blank name; UUID id.

    3. `src/domain/employee.rs`:
       `Employee { id, name, roster_id, position_id, #[serde(default)] skills: Vec<String> }`
       deriving the same traits.
       - `Employee::new(name, roster_id, position_id) -> Result<Self, DomainError>` trims the name and rejects blank; it cannot validate the references (Organization does); assign UUID.
       - `Employee::add_skill(&mut self, skill: &str) -> Result<(), DomainError>` trims, rejects blank or duplicate (case-sensitive), preserves insertion order.

    4. `src/domain/shift.rs`:
       `StaffingRequirement { position_id: String, headcount: u16 }`
       `ShiftTemplate { id, name, start: NaiveTime, end: NaiveTime, #[serde(default)] required_positions: Vec<StaffingRequirement> }`
       deriving the same traits.
       - `ShiftTemplate::new(name, start, end) -> Result<Self, DomainError>` trims/rejects blank names, rejects `start == end` with `InvalidShiftTimes` (equal times are ambiguous, not a 24-hour shift), assigns a UUID.
       - `duration_minutes(&self) -> u32`: minutes until `end`, adding 24h when `end < start`; a max 1439 at construction keeps this in `u32`.
       - `crosses_midnight(&self) -> bool`: `end < start`.
       - Do not model duty categories or a night/morning enum; Phase 3's rest rules reference shift ids.

    5. `src/domain/roster.rs`:
       `Roster { id, name, #[serde(default)] shifts: Vec<ShiftTemplate> }` deriving the same traits.
       - `Roster::new(name) -> Result<Self, DomainError>` trims and rejects a blank name, then assigns a UUID; duplicate names are checked by `Organization::add_roster`, since only the parent can see siblings.
       - `shift(&self, id) -> Option<&ShiftTemplate>` and a crate-visible `shift_mut`/`push_shift` used by `Organization`. Keep public mutators minimal: Organization is the supported entry point because it validates positions and roster membership.
       - No `positions`, `employees`, or constraint fields on `Roster` beyond what 02-02 adds (rest rules).

    6. `src/domain/organization.rs` — move the Phase 1 `Organization` here and extend it:
       `Organization { id, name, #[serde(default)] positions: Vec<Position>, #[serde(default)] employees: Vec<Employee>, #[serde(default)] rosters: Vec<Roster> }`
       - Keep `Organization::new(name)` and the existing field names.
       - Lookups: `position(id)`, `employee(id)`, `roster(id)`, plus `employee_mut(id)` and `roster_mut(id)` for methods/tests.
       - `employees_in_roster(&self, roster_id: &str) -> impl Iterator<Item = &Employee>` (or `Vec<&Employee>`) — this is the isolation read path; return an empty iterator for an unknown roster rather than panicking.
       - `add_position(name) -> Result<&Position, DomainError>`: reject blank/duplicate within the organization.
       - `add_roster(name) -> Result<&Roster, DomainError>`: reject blank/duplicate within the organization.
       - `add_employee(name, roster_id, position_id) -> Result<&Employee, DomainError>`: reject unknown roster and unknown position, then build via `Employee::new`.
       - `add_shift(roster_id, name, start, end) -> Result<&mut ShiftTemplate, DomainError>`: roster must exist; reject duplicate shift names within that roster; build via `ShiftTemplate::new` and push onto the roster.
       - `require_position(roster_id, shift_id, position_id, headcount) -> Result<(), DomainError>`: roster, shift, and organization position must exist; reject `headcount == 0`; update an existing requirement for that position or push a new one.
       - `validate(&self) -> Result<(), DomainError>`: unique ids across positions/employees/rosters (shifts unique within their roster); every `employee.roster_id` and `employee.position_id` resolves; every shift requirement position resolves. Rule references are added in 02-02.

    7. `src/domain/project.rs`:
       - Keep `ProjectFile` and `SCHEMA_VERSION` here; remove the `Organization` struct body and `pub use organization::Organization;` (or re-export from `domain::mod`) so existing `crate::domain::Organization` imports keep working.
       - Move the Phase 1 organization unit tests to `organization.rs` and keep them passing.
       - `ProjectFile::add_organization` keeps its `Option<&Organization>` signature and behavior.

    8. `src/domain/mod.rs`: declare `organization`, `position`, `employee`, `shift`, `roster`, `error`; re-export `DomainError`, `Employee`, `Organization`, `Position`, `Roster`, `ShiftTemplate`, `StaffingRequirement` alongside `ProjectFile`/`SCHEMA_VERSION`.

    Avoid: nesting employees under rosters (the corrected hierarchy); roster-scoped positions; validating only in the UI; using `Option` for names; adding trait objects or new crates.
  </action>
