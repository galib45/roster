<objective>
## Goal

Turn a generated plan into a Pumpkin CP model — one decision variable per seat, one presence literal per seat/employee — and post every hard Phase 3 rule as a real constraint, so a satisfaction solve always produces a plan with zero hard violations.

## Purpose

Phase 3 can only judge a plan, never produce one. This plan builds the solver's foundation so the app can move from "here is what is wrong" to "here is a roster that is right". Getting the hard half exact matters more than the objective: an overlap-free, leave-respecting roster is the minimum a hospital can ship, and every later convenience (fairness, preferences, UI) sits on top of it.

## Output

- `src/solver/mod.rs`: `SolveOptions`, `SolveStatus`, `SolveReport`, `SolveError`, and the internal build/solve entry points
- `src/solver/model.rs`: seat variables, employee presence literals, fixed assignments from the plan and its context
- `src/solver/constraints.rs`: overlap, unavailability, and rest constraints plus the fixed-input pre-check
- `pumpkin-solver` becomes a real dependency (the `unused_dependencies` allowance is deleted)
</objective>

<design>
## Confirmed Pumpkin 0.5 API (research done during planning)

| Need | API |
|------|-----|
| Integer variable | `solver.new_bounded_integer(lo, hi) -> DomainId` |
| Boolean | `solver.new_literal() -> Literal` (`Literal` is a 0/1 `IntegerVariable`) |
| Reification | `solver.add_constraint(<negatable>).reify(literal)` posts `literal ↔ constraint` |
| Sum equality | `pumpkin_solver::equals(terms, rhs, tag)` — every term coefficient is 1 |
| Linear inequality | `pumpkin_solver::less_than_or_equals(terms, rhs, tag)` |
| Abs / divide / product / max | `absolute`, `division`, `times`, `maximum` |
| Coefficients | `TransformableVariable::{scaled, offset}` (`AffineView`) |
| Solve | `solver.satisfy(&mut brancher, &mut termination, &mut resolver)` |
| Optimise | `solver.optimise(..., LinearSatUnsat::new(direction, objective, callback))` |
| Results | `SatisfactionResult::{Satisfiable, Unsatisfiable, Unknown}`, `OptimisationResult::{Optimal, Satisfiable, Stopped, Unsatisfiable, Unknown}` |
| Termination | `core::termination::{Indefinite, TimeBudget::starting_now(Duration)}` |
| Resolver | `pumpkin_solver::conflict_resolvers::resolvers::ResolutionResolver` |

**Type trick:** `equals` needs one homogeneous term type. Normalise every term to
`AffineView<DomainId>`: `domain.scaled(k)` gives that directly, and
`literal.get_integer_variable().scaled(k)` converts a literal into the same view.
Never mix `DomainId`, `Literal`, and `AffineView` in one term array.

## Seat model

```text
Seat {                       // one per ShiftSlot in the plan, in plan order
  dated_shift_id, slot_id,
  position_id, date, template_id,
  start, end, duration_minutes,
  eligible_employee_ids: Vec<String>,   // roster employees holding position_id, in roster order
}

seat_var[i]  ∈ 0..=n         // 0 = empty, e+1 = eligible_employee_ids[e]
works[i][e]  : Literal       // reified (seat_var[i] == e+1)
empty[i]     : Literal       // reified (seat_var[i] == 0)
```

- Employees are the plan roster's employees with the seat's position; employees
  from other rosters or other positions never enter the domain.
- A slot already holding an employee is **fixed**: `equals([seat_var], e+1).post()`.
- A slot holding an employee who is not eligible for that position is an input
  error (`SolveError::InconsistentInput`), not a silently dropped assignment.
- Seat order is the plan's own order (dated shifts in stored order, slots in
  stored order) so model construction and results are deterministic.

## Hard constraints (mirror `src/eval/rules.rs`)

| Phase 3 rule | Pumpkin encoding |
|--------------|------------------|
| Overlap, two dated seats | For every overlapping seat pair `(i, j)` and employee `e`: `less_than_or_equals([works[i][e], works[j][e]], 1)` |
| Overlap, context vs seat | For a fixed context assignment of employee `e` overlapping seat `i`: `less_than_or_equals([works[i][e]], 0)` |
| Hard unavailability | For each seat whose date/template matches a hard rule of `e`: `less_than_or_equals([works[i][e]], 0)` |
| Hard rest | For each rule `(preceding template, following template)` and each ordered pair of dated shifts with `earlier.start < later.start` and `gap < min_rest`: `less_than_or_equals([works[earlier][e], works[later][e]], 1)`. A context assignment matching the preceding template forbids the later seat; matching the following template forbids the earlier seat. |

Reuse Phase 3 matching logic rather than re-implementing it: expose
`eval::rules::{overlaps, rule_matches, interval}` as `pub(crate)` (or move the
shared helpers into a small `pub(crate)` module) so the solver and the evaluator
cannot drift apart. Do not change their behaviour.

## Fixed-input pre-check

Unfilled seats create no assignments, so **every hard violation in a plan comes
from an existing assignment** (prefilled slot or context). Therefore:

1. Run `evaluate(organization, roster_id, plan_id, &options.eval)`.
2. If `hard_count() > 0`, return `SolveError::InconsistentInput { reasons }` with
   one human-readable line per hard violation.
3. Otherwise the empty assignment is always feasible — coverage is never a hard
   constraint — so `Unsatisfiable` from the solver means a modelling bug, not bad
   input.

## Public surface (introduced here, completed in 04-02)

```rust
pub struct SolveOptions {
    pub eval: EvalOptions,            // multi-shift penalty semantics
    pub coverage_penalty: i64,        // 1_000_000
    pub fairness_weight: i64,         // 1
    pub soft_penalty_weight: i64,     // 60
    pub time_limit: Option<Duration>, // Some(30s)
}

pub enum SolveStatus { Optimal, Feasible, Infeasible, Unknown }

pub struct SeatAssignment { dated_shift_id, slot_id, employee_id: Option<String> }

pub struct SolveReport {
    status, assignments: Vec<SeatAssignment>, objective: Option<i64>,
    total_slots, unfilled_slots,
    coverage_cost: u64, fairness_cost: u64, soft_cost: u64,  // unweighted, filled in 04-02
    elapsed: Duration,
}

pub enum SolveError {
    Domain(DomainError),
    InconsistentInput { reasons: Vec<String> },
    ModelTooLarge { required: i64 },
    NoSolution,                       // apply() was handed an Infeasible/Unknown report
    Solver(String),                   // an impossible Unsatisfiable on a clean model
}
```

objective land in 04-02.

<acceptance_criteria>

## AC-1: The model mirrors the plan's seats
```gherkin
Given a Doctors roster with two Medical Officers and a plan with four seats
When the model is built
Then there is exactly one seat variable per slot, bounded 0..=2, in plan order
And each seat has one presence literal per eligible employee, and a literal that is true exactly when the seat is empty
And a seat already filled by a doctor is fixed to that doctor
And employees from another roster or another position are not in any seat's domain
```

## AC-2: Overlap is impossible
```gherkin
Given a plan with two seats that overlap in time on the same date
When the hard constraints are built and the model is solved
Then no employee is present in both seats
And an overlapping previous-day context assignment for an employee forbids that employee in the overlapping seat
And a model that additionally forces one employee into both seats is unsatisfiable
```

## AC-3: Hard availability and rest rules hold
```gherkin
Given an employee with a hard leave period, a hard weekly rule, and a hard rest rule
When the model is solved
Then the employee is never placed on a seat covered by a hard unavailability rule
And the employee is never placed on a later shift that violates the rule's minimum rest after an earlier shift or context assignment
And solving a model that forces the violating seat is unsatisfiable
```

## AC-4: Inconsistent fixed inputs are reported, not solved
```gherkin
Given a plan whose prefilled slot or context assignment already violates a hard rule
When solve is requested
Then it returns SolveError::InconsistentInput naming each hard violation
And the model is never handed to Pumpkin
```

## AC-5: The model is always satisfiable from a clean plan
```gherkin
Given a plan with no hard violations and no feasible employee for some seats
When the model is solved
Then a solution exists with those seats empty
And every filled seat in the solution belongs to an eligible employee
And a second solve of the same model produces the same seat assignment
```
