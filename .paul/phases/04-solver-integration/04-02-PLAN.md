<objective>
## Goal

Optimise the hard-feasible model: one weighted objective that fills coverage first, then minimises the same L1 fairness deviation the app reports, then honours soft penalties — and a `solve`/`apply` pair plus a CLI that turn a project JSON into a saved, evaluated roster.

## Purpose

A model that merely avoids illegal rosters is not the product. The value proposition is an *equitable* roster that keeps stated preferences when it can. This plan attaches the Phase 3 measure (`WorkloadReport::deviation_minutes`) to the solver as the objective, so the number the admin sees and the number the solver minimises are the same quantity.

## Output

- `src/solver/objective.rs`: coverage, fairness (L1 linearisation), and soft-penalty terms plus the objective bound
- `SolveOptions::default()` weights documented and enforced
- `solve()` → `SolveReport` with `Optimal | Feasible | Infeasible | Unknown`, and `apply()` writing assignments back with `PlanStatus::Generated`
- `tests/solver.rs`: end-to-end coverage of the solver through the public API
- `examples/solve.rs`: `cargo run --example solve -- --project <in> --out <out>`
</objective>

<design>
## Objective

```text
objective = coverage_penalty  * Σ empty[i]
          + soft_penalty_weight * soft_cost
          + fairness_weight   * Σ deviation[e]
```

Weights (`SolveOptions::default()`), fixed and documented in code, per the
phase decision:

| Weight | Default | Rationale |
|--------|---------|-----------|
| `coverage_penalty` | `1_000_000` | Large enough to dominate the entire fairness + soft maximum for any realistic plan, so coverage is effectively lexicographic |
| `fairness_weight` | `1` | One objective unit per unbalanced minute |
| `soft_penalty_weight` | `60` | One penalty unit costs about an hour of imbalance |

Units differ on purpose (seats, minutes, penalty units); the weights convert
them into one integer. `solve` computes the theoretical maximum of the
fairness and soft parts while building and returns
`SolveError::ModelTooLarge { required }` if the objective bound would exceed
`i32::MAX`.

## Fairness linearisation (mirrors `src/eval/fairness.rs`)

For every roster employee `e`:

```text
minutes[e]   = Σ duration(i) * works[i][e]                  // 0..=total_minutes
total        = Σ minutes[e]                                 // 0..=total_minutes
group_total  = Σ minutes[e] for e in group                  // 0..=total_minutes
mean[e]      = total / employee_count      (ungrouped)      // truncating division
             = group_total / group_size    (grouped)
signed[e]    = minutes[e] - mean[e]                         // -total..=total
deviation[e] = |signed[e]|
```

- Employers in a sharing group compare with their group's mean; everyone else
  with the roster mean over **every** roster employee, including zero-workload
  staff. Same rule as `eval::fairness`, so the objective targets the reported
  number.
- Division is Pumpkin's truncating integer division. The objective therefore
  minimises an integer approximation; `WorkloadReport::deviation_minutes` stays
  the authoritative score and is what tests and the UI read.
- Guard: add no fairness constraints when the roster has zero employees.

## Soft penalties (mirrors `src/eval/rules.rs`)

| Rule | Encoding |
|------|----------|
| Recurring preference `(employee e, weekday, template t, penalty p)` | For each dated shift `d` with template `t` on that weekday, skipping dates covered by a hard rule of `e`: `cost += p * (1 − Σ works[seats of d][e])`. Post `less_than_or_equals([works…], 1)` per `(e, d)` so the sum is 0/1 and the linearisation stays exact. |
| Multiple shifts in a day | Per `(e, date)` with `k ≥ 2` seats in `e`'s domain: `count = Σ works + context_count`, `excess = max(count − 1, 0)`, `cost += eval.multi_shift_penalty * excess`. Skip entirely when the penalty is 0. |
| Soft unavailability | Per matching `(seat, e, rule)`: `cost += rule.penalty * works[i][e]` |
| Soft rest | Per matching ordered pair with `gap < min_rest`: `both = works[a][e] * works[b][e]` via `times`, `cost += rule.penalty * both`; one context side collapses to `penalty * works[other][e]` |

Context assignments contribute a constant to recurring/multi-shift accounting
and cannot be changed; soft violations already present in the fixed input are
reported by `evaluate` after `apply`, not by the solver.

## Solve and apply

```rust
pub fn solve(&Organization, roster_id, plan_id, &SolveOptions) -> Result<SolveReport, SolveError>
pub fn apply(&mut Organization, roster_id, plan_id, &SolveReport) -> Result<(), SolveError>
```

- `solve` runs `precheck` → build → hard constraints → objective →
  `optimise(LinearSatUnsat::new(Minimise, objective, |_,_,_,_| ControlFlow::Continue(())))`.
- Status mapping: `Optimal → Optimal`, `Satisfiable → Feasible`, `Stopped → Feasible`,
  `Unknown → Unknown`, `Unsatisfiable → SolveError::Solver(..)` (a clean model can
  never be unsatisfiable; coverage is optional).
- `Feasible` means "best solution found within the time limit", not "optimal".
  Callers must treat it as usable, exactly like `Optimal`.
- `apply` refuses `Infeasible`/`Unknown` reports, refuses finalised plans, then
  **unassigns every seat before assigning any** (otherwise swapping two
  employees inside one dated shift trips `EmployeeAlreadyAssigned`), and finally
  sets `status = PlanStatus::Generated` and `updated_at`.
- Nothing is mutated unless the report is applicable, so a failed or timed-out
  solve leaves the plan exactly as it was.

## Harness

`examples/solve.rs` (not a second binary: another `src/bin` target would make
plain `cargo run` ambiguous and break the GUI smoke check).

```text
cargo run --example solve -- --project in.json [--out out.json]
                              [--roster <id|name>] [--plan <id>]
                              [--time-limit <seconds>]
```

Loads and validates the project, resolves the roster (default: first) and plan
(default: last), solves, prints status/objective breakdown/elapsed, applies,
saves, and prints the post-solve evaluation. Exit codes: `0` solved, `2`
infeasible/unknown, `1` error. Default output is `<input>.solved.json`; never
overwrite the input implicitly.

<acceptance_criteria>

## AC-1: Fairness is the reported deviation, linearised
```gherkin
Given two doctors in one sharing group with 360 and 1020 minutes of seats
When the objective is minimised
Then each doctor's deviation is measured against the group mean
And an ungrouped doctor is measured against the roster mean over every roster employee
And the solver's fairness cost on a balanced assignment is 0 while an unbalanced one is positive
And the post-solve WorkloadReport deviation is never worse than the pre-solve plan's
```

## AC-2: Coverage outranks fairness
```gherkin
Given a plan with a free seat and two eligible employees, one already heavily loaded
When the model is solved
Then the seat is filled, not left empty
And no seat is left empty when an eligible employee exists who does not violate a hard rule
```

## AC-3: Soft penalties are honoured when coverage allows
```gherkin
Given a recurring preference for Dr. Amit on Monday OPD
When the roster is solved and fairness does not force the other doctor
Then Dr. Amit holds an OPD seat that Monday
And when two employees could each take one of two same-day shifts, the solution splits them instead of giving one employee both
And a soft leave rule is avoided when an alternative employee is available
```

## AC-4: Statuses are honest and apply is safe
```gherkin
Given a solve that reaches proven optimality
When solve returns
Then status is Optimal and objective is present
And a time-limited solve that finds a feasible solution returns Feasible with usable assignments
And a plan whose fixed input violates a hard rule returns InconsistentInput without calling Pumpkin
And apply on an Infeasible or Unknown report leaves the plan unchanged
And apply on a finalized plan returns PlanFinalized
And a successful apply sets PlanStatus::Generated and writes every seat of the report
```

## AC-5: A solved project survives save and reload
```gherkin
Given a November-style project loaded from JSON
When it is solved, applied and saved, then reloaded
Then every assignment is preserved
And evaluate() on the reloaded project reports zero hard violations
And it reports the same deviation, soft penalty and coverage counts as before saving
```

## AC-6: The harness solves a project file end to end
```gherkin
Given a project JSON written by the store
When `cargo run --example solve -- --project <in> --out <out>` runs
Then it exits 0, writes <out>, and prints the status, costs, and post-solve evaluation
And `<out>` reopens with the assignments applied and zero hard violations
And the input file is unchanged
```
