<objective>
## Goal

Add a read-only evaluation layer that inspects a generated `RosterPlan` and reports every hard violation and weighted soft penalty the domain rules imply — overlapping assignments, unmatched unavailability/leave, unmet recurring assignments, insufficient rest (including previous-day context), and multiple shifts in one day — without calling the solver or mutating the project.

## Purpose

Phase 4 needs one set of semantics to encode into Pumpkin, and Phase 7 needs the same semantics to score manual edits live. Building evaluation now, over the data 02-03 just produced, keeps the solver from inventing its own rule logic and gives the UI a single source of truth for "is this roster legal, and what does it cost?"

## Output

- `src/eval/` module: `evaluate`, `Evaluation`, `Violation`, `ViolationKind`, `ShiftRef`, `EvalOptions`
- `ContextAssignment.template_id: Option<String>` so rest rules can match previous-day context
- Domain validation for the optional context template reference
- `tests/constraint_eval.rs` covering each hard rule, each soft rule, and context interaction
</objective>

<design>
## Evaluation API

```text
evaluate(org: &Organization, roster_id: &str, plan_id: &str, options: &EvalOptions)
    -> Result<Evaluation, DomainError>

EvalOptions { multi_shift_penalty: u32 }   // default 1; 0 disables the soft rule

Evaluation {
  violations: Vec<Violation>,
  total_slots: usize,
  unfilled_slots: usize,
}
Evaluation::hard_count() -> usize
Evaluation::soft_penalty() -> u64
Evaluation::is_feasible() -> bool        // hard_count() == 0

Violation { severity: Severity, penalty: u32, kind: ViolationKind }

ViolationKind
├── Overlap { employee_id, first: ShiftRef, second: ShiftRef }
├── Unavailable { employee_id, rule_id, shift: ShiftRef }
├── MissingRecurringAssignment { employee_id, assignment_id, date, template_id }
├── InsufficientRest { employee_id, rule_id, preceding, following, gap_minutes: i64 }
└── MultipleShiftsInDay { employee_id, date, shift_count: usize }

ShiftRef
├── Dated { id: String }
└── Context { date: NaiveDate, name: String }
```

## Evaluation rules

| Rule | Severity | Penalty | Notes |
|------|----------|---------|-------|
| Two assignments overlap in time | Hard | 0 | Includes context vs plan and plan vs plan; touching intervals (end == start) do not overlap |
| Assignment falls in an unavailability rule's scope | Rule's severity | Rule's penalty | `Weekly` matches weekday, `Date` exact, `Leave` inclusive; empty `shifts` = whole day, otherwise `template_id` must be listed |
| Recurring assignment is unmet | Hard | 0 | If the plan contains the template's dated shift for that weekday, the employee must occupy one of its slots |
| Rest between two rule-matched assignments < `min_rest_minutes` | Rule's severity | Rule's penalty | Ordered by start; gap is minutes from the earlier shift's end to the later shift's start. Negative gaps are overlap only |
| Employee has >1 dated shift starting on one date | Soft | `multi_shift_penalty × (count − 1)` | Skipped entirely when the option is 0 |

## Deliberate exclusions

- Unfilled slots are **reported**, not violations: the fairest solution may legitimately leave seats empty.
- Assignment mutation, status transitions, and constraint repair are out of scope.
- No new dependencies; `chrono` and `serde` only.
</design>

<acceptance_criteria>

## AC-1: Overlap and context are evaluated
```gherkin
Given a valid Doctors plan with filled slots
When the same employee holds two assignments whose time ranges intersect
Then evaluate() reports one Hard Overlap naming both shifts and the employee
And two assignments that merely touch (one ends exactly when the other starts) do not overlap
And an assigned context shift that intersects a day-one dated shift is reported
```

## AC-2: Unavailability, leave, and recurring demand are evaluated
```gherkin
Given an employee with weekly, date, and leave unavailability plus recurring assignments
When the plan assigns them during a matching scope or leaves a recurring shift unfilled
Then evaluate() reports Hard Unavailable for each matched assignment and Hard MissingRecurringAssignment for each unmet recurring demand
And soft unavailability yields a Soft violation whose penalty comes from the rule
And a shift-scoped rule only matches the listed template, while an empty shift list matches every shift
```

## AC-3: Rest, multi-shift days, and penalty totals are evaluated
```gherkin
Given roster rest rules and assignments
When two rule-matched assignments have less than the required gap
Then evaluate() reports InsufficientRest with the actual gap and the rule's severity/penalty
And a night assignment followed by the next morning's assignment at a 0-minute gap is reported
And an employee with two non-overlapping shifts starting on one date produces one Soft MultipleShiftsInDay violation per extra shift
And soft_penalty() equals the sum of soft penalties, while hard_count()/is_feasible() reflect hard violations only
```

## AC-4: Context can be matched to templates
```gherkin
Given a ContextAssignment with a template_id naming one of the roster's shifts
When the project is saved and loaded and validated
Then the template_id round-trips and validates successfully
And a ContextAssignment naming an unknown or out-of-roster template is rejected
And context assignments without a template_id (older files) still load and evaluate, matching only whole-day rules
```

## AC-5: Evaluation is read-only and covers unfilled work
```gherkin
Given a generated plan
When evaluate() runs repeatedly
Then the organization, roster, and plan are unchanged and results are identical
And total_slots/unfilled_slots match the plan's own counts
And an unknown roster or plan returns the corresponding DomainError
```
